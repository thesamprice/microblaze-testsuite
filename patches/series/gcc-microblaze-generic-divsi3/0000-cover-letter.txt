libgcc: microblaze: use the generic C for 32-bit division

MicroBlaze has hand-written __divsi3, __modsi3, __udivsi3 and __umodsi3
(libgcc/config/microblaze/*.S).  This patch replaces them with libgcc's
divmod.c, udivmod.c and udivmodsi4.c, as iq2000 and pdp11 do.  They are
only called on cores without a divider: with -mno-xl-soft-div gcc emits
idiv.

It is a trade-off, not a clear win.  The C is faster on average, much
faster for short quotients, slower for long ones, and its worst case is
about 50% higher.

Instructions executed per call (mean) and estimated cycles per call,
mean (max), over 2000 operand pairs per set, big-endian:

  c5   five-stage pipeline (C_AREA_OPTIMIZED=0), no branch target cache
  cb   five-stage with a perfect branch target cache: one cycle per
       instruction
  c3   three-stage pipeline (C_AREA_OPTIMIZED=1)

__umodsi3 costs within 2 cycles of __udivsi3, and __modsi3 within 3 of
__divsi3, except that the C __modsi3 without the barrel shifter costs
about 33 cycles more.  The assembly has no variants, so its column never
changes; the C gains about 5% from the options.  With the divider too, the C is
unchanged (udivmodsi4.c is a shift loop and never uses /), and inline
idiv costs 36 cycles (c5) for a quotient and 38 for a remainder.

"random" is a 32-bit dividend and a divisor of random bit length; "short
q" has quotients from 0 to 15; "long q" has divisors from 1 to 15.  The
signed routines get operands of both signs, the unsigned ones operands
taken as unsigned.

Why: udivmodsi4.c shifts the divisor up one bit at a time until it
passes the dividend, then subtracts one bit at a time, so it runs two
loops each as long as the quotient.  The assembly shifts the dividend
left past its leading zeros, then runs one loop over the remaining bits.

The cycle counts are estimates.  The plugin costs each executed
instruction with UG984's per-instruction latencies and assumes
single-cycle local memory.  Data-hazard stalls, counted separately, add
at most 2 cycles per call to the C and none to the assembly.  I have
not measured cycles on hardware.

Correctness: libgcc-audit's boundary and random tables, about 700,000
pairs per endian, give 0 mismatches for the C on big- and little-endian
with no options, -mxl-barrel-shift, -mno-xl-soft-mul,
-mxl-pattern-compare and every option.  Division by zero still returns
0, except that 0 / 0 is now 1.

Tested with make check-gcc (gcc.c-torture/execute and
gcc.target/microblaze) on qemu-system-microblaze, big-endian, against
gcc master df809a029 with the other runner patches: 24536 and 770
passes, no failures, the same as without this patch.
