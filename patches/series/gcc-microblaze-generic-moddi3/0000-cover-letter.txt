libgcc: speed up no-divider modulo, drop moddi3.S

MicroBlaze has a hand-written 64-bit signed remainder,
libgcc/config/microblaze/moddi3.S.  It was fixed in 3a721dc02.  This
series replaces it with libgcc2.c's generic code, with two changes to
that code for targets without a hardware divider.

1/3 makes libgcc2.c's shift-and-subtract __udivmoddi4 take the low
quotient bits with a mask in __udivdi3 and __divdi3, which do not want
the remainder.  That saves two variable double-word shifts, and on a
target without a barrel shifter a variable double-word shift is a loop.
The preprocessor selects it, so the exported __udivmoddi4 and the other
inlined copies compile to the same code as before.

2/3 adds a shift-and-subtract loop for __umoddi3 and __moddi3 that keeps
only the remainder, and decides each step from the sign of one
subtraction.  It is faster on MicroBlaze and slower on armv6-m, so a
target opts in by defining LIBGCC2_MOD_WITHOUT_QUOTIENT, which is
documented in tm.texi.  No target defines it in this patch.

Both patches only change code under TARGET_HAS_NO_HW_DIVIDE.  No x86 or
AArch64 configuration defines it, so those libgcc builds do not change.

3/3 is MicroBlaze only.  MicroBlaze's divider is optional, and no
multilib in t-microblaze enables it.  A new microblaze-lib.h defines
TARGET_HAS_NO_HW_DIVIDE and LIBGCC2_MOD_WITHOUT_QUOTIENT unless
-mno-xl-soft-div is given.  Without a divider, all four routines then
use shift and subtract, and __moddi3 comes from libgcc2.c.  moddi3.S
goes.  With -mno-xl-soft-div the generic C uses the divider.  moddi3.S
could not, and today libgcc uses it even when it is built for a core
with a divider.

Mean instructions per call over 4701 operand pairs, on QEMU with
-icount, big-endian:

                 no options       barrel shifter,   every option,
                                  hw multiply       with the divider
                 before   after   before   after    before   after
  __moddi3        522.5   457.0    522.5   275.3     522.5    91.7
  __umoddi3       921.1   338.0    625.6   197.2      54.3    54.3
  __divdi3       1303.3  1312.7    903.7   338.4      88.4    88.4
  __udivdi3       891.1   951.0    626.7   245.4      44.2    44.2

"Before" for __moddi3 is moddi3.S in every column.  The one regression
is division with no options: __divdi3 0.7% and __udivdi3 6.7% slower on
average, with a worse worst case.  Shift and subtract costs more than
long division when the quotient is long, and less when it is short.

On Cortex-M0 (armv6-m), which defines TARGET_HAS_NO_HW_DIVIDE but not
the new macro, measured on QEMU's microbit machine with the routines
built by arm-none-eabi-gcc 14.2 at -O2:

                       before   after
  __aeabi_ldivmod       487.7   483.6
  __aeabi_uldivmod      249.1   249.1
  __udivdi3             229.9   207.3
  __divdi3              406.5   402.3
  __moddi3              280.7   280.7
  __umoddi3             193.6   193.6

On ARM EABI, C's 64-bit / and % call __aeabi_ldivmod and
__aeabi_uldivmod.  Nothing gets slower, and the routines left at the
same count compile to the same code.  2/3 is opt-in because an earlier
version applied it to every target without a divider, and on Cortex-M0
it made __moddi3 and __umoddi3 27% and 46% slower: ARM shifts a double
word left in two instructions and compares with flags, so
__udivmoddi4's existing loop suits it.

Tested with gcc.c-torture/execute.exp on qemu-system-microblaze,
machine petalogix-s3adsp1800, against gcc master df809a029:
big-endian, little-endian, and with libgcc, newlib and the tests built
for the divider and every other option.  Each gave 24536 passes and the
same 14 failures, none of them in division (fprintf-2.c needs a
filesystem; pr117432.c is a separate variadic bug).  libgcc also builds
for microblaze-rtems7 and microblaze-linux in every multilib.  On an
earlier version of the series with the same remainder loop, coverage
measured with a QEMU plugin showed the torture tests reach every line
and branch of the new code.
